# 从文件上传到向量入库：一个 RAG 知识库 ingest 管道的完整实现

> 本文以 Next.js + Redis + Milvus 搭建的知识问答系统为例，拆解一个生产可用的文档入库管道：用户点下"上传"按钮之后，文件经历了哪些环节，才变成可以被语义检索的向量。

## 一、为什么不能"上传完直接向量化"

先明确一个前提：**Embedding 是一个慢操作**。

一个 20MB 的文档解析出的文本可能有几十万字符，切成几百个 chunk 后，调用一次 Embedding API 需要数秒到几十秒。如果把这个过程放在 HTTP 请求里同步等待：

- 请求极易超时（很多网关默认 30s 上限）；
- 用户对着转圈圈的页面没有任何反馈；
- 多用户同时上传时，并发 embedding 会打爆 API 限流。

所以这个系统把流程拆成了**同步的"接收与解析"**和**异步的"切分与向量化"**两段，中间用一个 Redis 队列衔接。

## 二、整体架构

```
浏览器                Next.js API                后台消费循环            外部服务
┌─────────┐  ①XHR上传  ┌──────────────┐  ②入队   ┌──────────┐  ③BLPOP  ┌────────────┐
│ 上传组件 │ ─────────→ │ POST         │ ───────→ │ Redis    │ ───────→ │ ingest:    │
│ (进度条) │            │ /api/documents│ LPUSH    │ List队列 │          │ 切分→Embedding
└────┬────┘            └──────┬───────┘          └──────────┘          │      ↓     │
     │ ⑤SSE推送状态           │ 落库(status=pending)                    └─────→ Milvus│
     │←────────────────────── │                                          向量数据库   │
     └──────────────────────────────────────────────────────────────────┘
```

一条文档的生命周期对应数据库里的四个状态：

`pending`（已入库，等待处理）→ `processing`（正在向量化）→ `ready`（可检索）/ `failed`（失败，可重试）

## 三、第一步：接收上传（同步、快速响应）

### 3.1 前端：用 XHR 而不是 fetch

上传组件通过隐藏的 `<input type="file">` 选择文件，然后用 `XMLHttpRequest` 发送 `multipart/form-data`。原因很实际：**fetch 拿不到上传进度事件，XHR 可以**。

进度条的设计有个小细节——分两段计费：

- `0 ~ 90%`：浏览器到服务端的真实上传进度（`xhr.upload.onprogress`）；
- `90 ~ 100%`：留给服务端的解析入库时间。

这样进度条不会"假跑"到 100% 再卡住，体验上更诚实。

### 3.2 服务端：先校验，再解析，立即落库

`POST /api/documents` 的处理顺序是刻意的：

1. **鉴权**：从会话里拿到用户和租户（知识库是租户内共享的）；
2. **白名单校验**：只接受 `txt / md / html / pdf / docx`，其余格式直接 400；
3. **大小校验**：单文件上限 20MB；
4. **解析文本**：按扩展名路由到对应解析器——

| 格式 | 解析方式 |
|------|---------|
| txt / md | 直接 UTF-8 读字符串 |
| html / htm | cheerio 去掉 script/style/nav/footer/header，只留 body 正文 |
| pdf | pdf-parse 提取文本层 |
| docx | mammoth 提取纯文本 |

解析器按格式插件化组织在一个 `extractText` 函数里，扫描件 PDF 这种解析为空的场景，留了一个 OCR/VLM 的扩展点（`TODO` 注释标记）。

5. **落库为 `pending`**：把原文、文件二进制、文件名、租户、属主一次性插入数据库；
6. **入队后立即返回 202**：响应体里带上文档 id，告诉前端"收下了，接下来看状态推送"。

关键决策：**解析文本这一步放在同步流程里**。如果解析失败（比如加密 PDF），可以在请求内直接返回 422 和明确错误信息，用户能立刻看到"这个文件有问题"，而不是上传成功后才在状态列表里看到一个失败标记。同时解析出的文本随队列消息传递，消费端不需要再读一次文件。

## 四、第二步：异步消费（Redis 队列 + 后台循环）

### 4.1 为什么用 Redis List 而不是重量级 MQ

这个量级（个人/小团队知识库）用 Redis List 做队列完全够用，而且有两个实打实的好处：

- **阻塞拉取**：消费端用 `BLPOP` 阻塞等待，队列空时不空转烧 CPU，有新任务立即唤醒；
- **天然适配多实例**：多个 Node 进程都执行 `BLPOP`，任务会被自动分摊，不需要额外的调度器。

入队用 `LPUSH`、消费用 `BLPOP`，是经典的生产者-消费者模型。

### 4.2 消费循环：每个进程只起一个

`enqueueDocument` 首次被调用时启动一个后台 `for(;;)` 循环：`BLPOP` 拿到任务 → JSON 反序列化 → 处理 → 回到阻塞等待。出错时 sleep 3 秒再续，保证循环永不退出。

### 4.3 防重锁：同一文档只处理一次

一个细节：如果因为网络重试、页面刷新导致同一文档被入队两次怎么办？

消费端用 Redis 的 `SET key "1" EX 1800 NX` 做了一把**分布式锁**——只有第一个拿到锁的进程会真正处理，后来者直接丢弃。锁带 30 分钟 TTL，即使进程崩溃也不会让僵尸任务永久占位。

## 五、第三步：向量化管道（切分 → Embedding → Milvus）

拿到锁之后，真正的工作交给 `ingestDocument`，它是整个管道的核心：

### 5.1 递归字符切分（Chunking）

使用 LangChain 的 `RecursiveCharacterTextSplitter`，参数：

- `chunkSize: 800`（字符）
- `chunkOverlap: 120`

递归切分会优先按段落、句子边界断开，尽量避免把一个完整的句子拦腰截断。重叠的 120 字符保证跨 chunk 的上下文不被切断——检索时即使答案横跨两个 chunk，也至少有一个 chunk 是语义完整的。

每个 chunk 包装成 LangChain `Document`，metadata 里带上 `documentId`、`filename`、`chunkIndex`、`tenantId`。**这份 metadata 是整个 RAG 检索的锚点**：后面删除文档要按 `documentId` 批量删向量，多租户检索要按 `tenantId` 过滤。

### 5.2 Embedding：走 OpenAI 兼容协议

Embedding 客户端不做任何厂商绑定，只用 `OpenAIEmbeddings` + 可配置的 `baseURL`。这意味着：

- 云上可以用 OpenAI / DeepSeek；
- 本地可以用 Ollama；
- 企业内部可以接自己的 LLM 网关。

切完的 chunks 一次性调用 `embedDocuments`，拿到一个 `N × dim` 的二维向量数组。

### 5.3 写入 Milvus：两处防御性校验

写入前有两道针对向量数据的防线（这来自真实的踩坑经验）：

1. **形状校验**：向量数组的行数必须等于 chunk 数，杜绝"有的 chunk 没 embedding 成功"的数据静默丢失；
2. **维度校验**：先从 Milvus 读出集合的 `dim` 参数，确认和 embedding 模型输出维度一致再写入。维度不匹配写入会报错，但错误信息往往晦涩难懂，提前校验能把故障定位时间从几小时缩短到几秒钟。

集合索引用 `IVF_FLAT + COSINE`（余弦相似度），`nlist: 1024 / nprobe: 10`，在召回率和查询延迟之间是个稳妥的默认值。

### 5.4 状态回写与失败处理

- 成功：`status → ready`，记录 `chunkCount`，通过事件总线广播；
- 失败（embedding API 挂了、Milvus 连不上等）：`status → failed`，把错误信息原样存进 `error` 字段，前端列表直接展示，并提供"重试"入口。

**失败不等于丢弃**：原文还在数据库里，重试按钮就是重新入队一次。

## 六、第四步：状态怎么实时同步到浏览器（SSE + Redis Pub/Sub）

消费循环跑在后台，前端怎么知道文档处理完了？答案是 SSE（Server-Sent Events）+ Redis Pub/Sub 的组合：

1. 队列处理过程中，每次状态变更都调用 `publish(tenantId, "document", {...})`；
2. 发布者把消息推到 Redis 的 `kqa:events:tenant:{tenantId}` 频道；
3. 浏览器的 `EventSource` 长连接挂在 `/api/events` 路由上，服务端 subscribe 对应租户频道，收到消息后推给浏览器；
4. 前端的 `useDocumentEvents` hook 收到事件后，**精准修改 TanStack Query 缓存里那一条文档记录**，而不是整页重新拉取。

为什么中间要隔一层 Redis Pub/Sub？因为上传进程、SSE 进程、消费进程可能跑在**不同的 Node 实例**上（多实例部署时尤其常见），进程内的内存事件总线传不过去，Redis 是跨实例的广播通道。

SSE 断线时浏览器会自动重连，前端还加了一层兜底：onerror 时 invalidate 一次查询，保证状态最终一致。

## 七、值得总结的几个设计决策

| 决策 | 收益 |
|------|------|
| 上传同步、向量化异步 | 接口毫秒级返回，不会超时；慢操作对用户透明 |
| 解析在请求内做 | 坏文件当场报错，不用等异步失败 |
| 文本随队列消息传递 | 消费端无状态，不需要回头读数据库/文件 |
| Redis `SET NX` 防重锁 | 重复入队不会重复处理，幂等 |
| metadata 带 tenantId | 向量检索按租户过滤，多租户隔离零成本 |
| 写库前维度校验 | 故障秒级定位，不写脏数据 |
| SSE + 精准缓存更新 | 实时性好，无轮询开销 |

## 八、还可以怎么演进

- **OCR / 多模态**：扫描件 PDF、图片走 VLM 识别，补全 `extractText` 的扩展点；
- **队列持久化升级**：任务量大时迁移到 BullMQ（基于 Redis 的成熟任务队列，自带重试、延迟、进度上报）；
- **增量入库**：大文件按 chunk 流式 embedding，避免单次 API 调用过大；
- **处理进度细化**：目前只有三态，可以把 `chunkCount / totalChunks` 也广播出来，前端展示"正在向量化 45/213"。
